# Prompt 工程说明

8 份 prompt 全部是 Markdown，放在 `src/resume_copilot/prompts/`，运行时可读、可 diff、可热改（改完重跑即可，不需要重新打包）。

## 一、统一的四段式结构

每份 prompt 都按同样的骨架写，模型才能在多个角色之间保持一致的行为基线：

```
1. 角色（你是谁、你的职责边界、你不做什么）
2. 输入（用 {{变量}} 显式占位，变量由 agents/roles.py 装配）
3. 硬约束（禁止事项、字数、字段名、单位）
4. 输出 JSON schema（带一个最小示例）
```

`system_common.md` 会被拼在**每个**角色 prompt 之前，承载三条全局铁律：禁止编造、只输出 JSON、中文输出；以及写简历的语言规则（动词+对象+数字+结果、空话清单、单条 60–96 字）。

## 二、几条刻意的设计

### 1. 变量用 `{{name}}`，不用 `str.format`

Prompt 里大量出现 JSON 花括号，用 `%` 或 `format` 会互相打架。`render_prompt()` 只替换 `{{xxx}}`，未提供的变量替换成空字符串，避免把 `{{jd_text}}` 原样发给模型。

### 2. 每个 prompt 都写"你会被怎么追问"

例如 `writer.md` 结尾直接列出三条"最容易犯的错"，`critic.md` 要求 `fix` 必须是**可直接替换的句子**。这是把评审标准前置到生成侧，比事后挑错便宜。

### 3. 输出契约写成可执行的 schema

`normalize_*()` 会再兜一层：模型少写字段就补默认，类型不对就纠正，因此 prompt 里的 schema 是"期望形状"，不是"唯一防线"。

### 4. 事实引用是显式字段

`bullets[].fact_refs` 让模型必须为每句话挂上事实 ID。这既是给机器校验用的锚点，也是一种心理约束——要求它"先说清依据再动笔"。

### 5. 温度按角色分配

| 角色 | 温度 | 原因 |
| --- | --- | --- |
| 事实库构建员 | 0.1 | 抽取任务，越低越稳，不许发挥 |
| 质检员 / 调研员 | 0.2 | 判断任务，需要一致的标准 |
| 定位 / 撰写 | 0.5 | 需要一点表达张力，但仍在事实边界内 |
| 面试教练 | 0.6 | 口播稿需要口语感 |

## 三、调 prompt 的正确姿势

1. **先看 `steps/` 里的中间产物**，确定问题出在哪个角色，不要一上来改 writer。
2. **改一个变量再跑**：`--rounds 0` 可以只看首稿，快速对比两次写作差异。
3. **用 mock 回归**：改 prompt 后跑 `python -m unittest discover -s tests -t .`，确保 JSON 结构没破。
4. **别把规则写成形容词**：「要具体」不如「每条要点必须包含一个数字或一个专有名词」。

## 四、失败模式与对策

| 现象 | 常见原因 | 对策 |
| --- | --- | --- |
| JSON 解析失败 | 模型加了围栏或解释 | `llm.json()` 自动回喂修复一次；仍失败则抛错并留档 |
| 简历里出现事实库没有的数字 | writer 自作主张 | `verify.check_numbers()` 直接报 error，触发修订 |
| 要点写成流水账 | 事实库粒度太粗 | 让 fact_extractor 拆得更细（一条事实一个动作），writer 才有料可选 |
| 关键词覆盖低 | JD 分析员关键词取太宽 | 把 `keywords` 限制在 8–16 个、长度 ≤8 字 |
| 一页装不下 | 要点太多 | prompt 限 18–26 条；渲染器再自动收紧字号兜底 |
| 两个模块讲同一件事 | 策略师没做取舍 | strategist 的 `omit` 与 `highlight_fact_ids` 必须显式给出 |

## 五、新增 prompt 的清单

- [ ] 有明确的"你不做什么"（防止角色越界）
- [ ] 所有输入都用 `{{变量}}` 占位，并在 `agents/roles.py` 的 `*_vars()` 里装配
- [ ] 硬约束写成可判定的句子（数字、字数、字段名）
- [ ] 给一个最小 JSON 示例，字段名与 `schemas.normalize_*()` 一致
- [ ] 在 `docs/agent-roles.md` 的角色表里补一行
