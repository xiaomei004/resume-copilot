# 开发实录：这个项目是怎么被做出来的

> 这份文档记录**开发过程本身**：需求怎么变成设计、Agent 怎么协作、技术难点怎么解、哪些验证做了、
> 哪些没做。想了解"用了会踩什么坑"看 [lessons.md](lessons.md)；想了解结构看 [architecture.md](architecture.md)。

## 一、从需求到设计

### 原始需求（用户给的 7 条 + 后续 4 条）

1. 复刻"把 JD + 旧简历变成定制简历 + 面试速查卡"的工作流，做成项目；
2. 符合 git 开发流程，托管到 GitHub；
3. 起点是材料输入（JD / 多份旧简历 / 补充信息），终点是简历 + 速查卡，中间 Agent 协作自行规划；
4. 需要一个 API_KEY，让使用者自己填；
5. 缺信息要主动问；
6. 给外接 LLM 设定角色，内部子 Agent 有角色与权限，遵循 prompt 工程；
7. 初版覆盖计算机相关岗位（研发 / 实施 / 市场），最好能泛化。
8. 后续追加：writer 拆岗位变体、coach 拆岗位变体、把踩坑写成学习笔记、CI 跑通、个人信息脱敏。

### 第一件事不是写代码，是拆流程

我把"手工做一份定制简历"的真实动作拆成 8 步，再决定每一步交给谁：

| 步骤 | 人造怎么做 | 交给谁 | 理由 |
| --- | --- | --- | --- |
| 读 JD、猜筛人逻辑 | 通读 + 圈关键词 | 模型（jd_analyst） | 语言理解，模型强 |
| 查公司与面经 | 搜网页、翻帖子 | 模型 + 检索（researcher，可选） | 需要外部信息，必须可关掉 |
| 翻旧简历找料 | 逐条摘、记数字 | 模型（fact_extractor，低温 0.1） | 抽取任务，要求稳 |
| 定主线、决定删什么 | 判断"投这个岗位该讲哪个故事" | 模型（strategist） | 需要取舍判断 |
| 写句子 | 逐条改写 | 模型（writer） | 表达任务 |
| 数字对不对、有没有空话 | 肉眼核 | **代码**（verify） | 可判定，别交给模型自评 |
| 排一页、别溢出 | Word 里调 | **代码**（render + LibreOffice + pymupdf） | 可测量 |
| 准备面试话术 | 手写稿 | 模型（coach） | 表达任务 |

**关键判断**：凡是"能被机器判定"的（数字有没有出处、几页、关键词覆盖率、条目长度），一律写成代码；
只有"需要判断与表达"的才交给模型。这条原则后来救了很多次（见 lessons.md 第 4、5 条）。

### 技术选型（当时为什么这么选）

| 决策 | 选择 | 理由 | 代价 |
| --- | --- | --- | --- |
| 形态 | CLI + Web 双入口 | CLI 便于自动化与 CI，Web 便于演示 | 多维护一个 FastAPI 层 |
| 模型接入 | OpenAI 兼容 + 可换 BASE_URL | 一份代码跑 DeepSeek / OpenAI / 通义 / 本地 vLLM | 用不到各家的专有能力 |
| SDK | **不用** openai SDK，只用 `urllib` | 降低安装门槛（只依赖 python-docx 就能跑） | 自己处理重试/超时/编码 |
| 输出格式 | DOCX + PDF + PNG | 投递要 PDF，改字要 DOCX，检查排版要 PNG | 依赖 LibreOffice（已做降级） |
| 检索 | 可选插件（Tavily） | 无 key 也能跑 | 检索质量受限于单一 provider |
| 结构化 | 全流程 JSON 契约 | 可校验、可 diff、可下载再改 | prompt 更长，模型更易出错（已加容错） |

## 二、Agent 协作：开发期与运行期

### 运行期（产品里的 8 个 Agent）

见 [agent-roles.md](agent-roles.md)。一句话：**能上网的不写简历，写简历的不上网；批评的不改稿，改稿的不自评。**

### 开发期（我这次实际怎么协作）

这次开发本身也是多 Agent 的：

1. **三个调研子 Agent 并行**：
   - 调研 A：某网络设备公司的行业地位、校招流程、面试形式（要求带来源与发布时间，标可信度）；
   - 调研 B：销售岗简历写法（要求给可直接套用的句式）；
   - 调研 C：研发岗简历写法（要求区分官方指南与社区经验）。
2. **分工原则**：子 Agent **只产调研，不碰代码**。代码由主 Agent 写、由本地脚本验证。
   原因是子 Agent 看不到本地文件状态，改代码容易互相踩。
3. **调研如何使用**：不直接抄进产品，而是先落到"设计约束"——
   比如"研发简历别写代码行数""技术岗写'沟通能力强'是零信息"，最后变成 `writer.rnd.md` 的一条规则。
4. **验证不只靠模型**：调研结论里"官方 JD 原文 / 上市公司披露"才当事实，社区面经一律标"可信度中"，
   代码里也只把前者写进 prompt 的示例。

### 一次典型的迭代循环（以 writer 为例）

```
写 prompt → 用真实 key 跑一遍 → 看 steps/*.json 定位是哪一步错
   → 只改那一步的 prompt 或代码 → 再跑 → 对比 manifest.json 的 quality
```

实跑 4 次（销售 2 次、研发 2 次），每次约 5.5 万 token，才把"硬错误 3 → 0""关键词 19% → 50%"压下来。
**prompt 是靠实跑调出来的，不是靠想出来的**。

## 三、技术说明

### 1. 分层

```
ingest（读材料） → agents（8 个角色 + prompt） → pipeline（编排 + 闸门） → render（DOCX/PDF/PNG） → cli / web
```

依赖方向单向向上，`render` 不认识业务，`agents` 不认识文件系统，`pipeline` 是唯一知道全局顺序的地方。

### 2. 四份 JSON 契约

`jd_profile` → `facts` → `positioning` → `resume`（+ `card`）。每份都有 `normalize_*()`
做"脏输入收敛"：缺字段补默认、类型错就纠正、多余字段丢弃。模型可以出格，结构不会崩。

### 3. Prompt 变体：底座 + 叠加

```
system = system_common.md + <角色底座>.md + <角色>.<role_family>.md
```

- 底座只放岗位无关内容（版式约束、schema、事实边界）；
- 变体只放岗位相关判断（模块顺序、筛人标准、语言、配比）；
- `resolve_prompts()` 找不到变体就只用底座，**新增岗位族不打断老流程**；
- `AgentSpec.variant_stem` 允许复用别人的变体（修订员复用 writer 的，避免改稿时忘掉岗位规则）；
- `trace.jsonl` 记录每个 Agent 实际用了哪几个 prompt 文件。

### 4. 确定性闸门（4 个检查 + 阈值）

| 检查 | 级别 | 做法 |
| --- | --- | --- |
| 数字溯源 | error | 抽简历中带单位/百分号/≥100 的数字，逐个与事实库比对（千分位归一；"从 0 到 1"这类修辞数字跳过） |
| 事实引用 | error | `fact_refs` 必须存在于事实库，悬空即报错 |
| 结构完整性 | error | 缺姓名/缺模块/role 空内容 |
| 行业词泄漏 | error | "政府客户/金融客户"等词出现但事实库没有该行业经历 |
| 空话与超长 | warn | 黑名单 12 词；单条 >96 字 |
| 关键词覆盖 | warn | <35% 且检查词 ≥6 个 |
| 速查卡时长 | warn | 口播稿 >700 字（超时）或 <480 字（撑不满） |

### 5. 多轮修订 + 保留最优

每版按 `-errors*10 - len(issues)` 打分，只保留最高分版本，并把每轮分数写进 `manifest.json`。
这不是过度设计：实测第 3 轮会比第 1 轮更差。

### 6. 渲染：数据驱动 + 单页收紧

- `docx_builder` 只认 `header + sections + role/bullet/text`，不认识岗位；
- 主题（颜色/字号/边距）与内容分离，按岗位族自动选；
- 角色行按"文字宽度估算（CJK 1 em / ASCII 0.55 em）"自动收字号，防长组织名把日期挤到下一行；
- 渲染 → 转 PDF → 数页数 → 超 1 页就按 3.5% 递减重排（≤6 轮，字号下限 8.6pt）；
- PDF 转换抽象成"能力位"：soffice 或 `RESUME_CONVERT_CMD` 任一可用即可。

### 7. 降级矩阵

| 缺什么 | 行为 |
| --- | --- |
| 检索 key | researcher 记 `skip`，其余照常 |
| LibreOffice / 转换命令 | 出 DOCX，`render.note` 说明"未校验页数" |
| pymupdf | 不出预览图、不数页数 |
| 视觉模型 | 跳过图片版 JD，提示改文本 |
| 模型 JSON 不合规 | 剥围栏/修引号/回喂修复，仍失败才抛错 |

### 8. 留痕

`steps/NN_*.json`（每步输入输出）、`logs/trace.jsonl`（耗时/权限/prompt 链）、
`manifest.json`（质量、token、产物）、`report.md`（给人看的总结）。
任何一个产物都能回答"这句话是谁写的、依据哪条事实、花了几次调用"。

## 四、验证矩阵

| 验证 | 覆盖 | 状态 |
| --- | --- | --- |
| 单元测试（47 个） | JSON 容错、闸门规则、变体解析、渲染结构、PDF 工具、端到端 mock | ✅ 全绿 |
| 端到端 mock | 六步流水线 + 产物 + 报告 + 速查卡 | ✅ 通过（0 token） |
| 真实模型实跑 | 销售 ×2、研发 ×2（每次约 5.5 万 token） | ✅ 一页、0 硬错误 |
| 版式核查 | PDF 的 bbox 坐标（不是文本抽取） | ✅ 无溢出、日期同行 |
| CI | ruff + unittest + mock 冒烟 | ✅ 见 GitHub Actions |
| 面试提问质量 | 人工阅读速查卡 | ⚠️ 只做了样例检查，没有量化 |
| 多岗位泛化 | 只验证了 3 个岗位族 | ⚠️ 未验证"实习/校招/社招"的差异 |

**没做的验证（诚实说明）**：没有做过 A/B（换了 prompt 后真实面试通过率如何），
所以本项目的价值主张是"省时间 + 不踩硬坑"，不是"提高录用率"。

## 五、技术决策记录（ADR 摘要）

1. **不用 openai SDK**：用户 clone 下来只需一个依赖即可跑；代价是自己写重试/超时/编码，已在 `llm.py` 处理。
2. **全流程 JSON 契约**：为了让"人也能接管"——`steps/*.json` 可以手动改完再重跑渲染，不必重跑模型。
3. **保留最优而不是最后一版**：LLM 修订不是单调改进。
4. **权限隔离**：把"不许编造"从 prompt 文本变成结构约束（写简历的拿不到检索通道）。
5. **PDF 转换可插拔**：外部二进制依赖必须能替换、能降级，否则 CI/无 GUI 环境直接瘫痪。

## 六、如果继续做

- **多 JD 批量**：一次投十个岗位，输出差异报告（哪条要点该删、哪条该提到前面）；
- **A/B 评估**：用同一份材料跑两版 prompt，人工盲评，积累"哪种写法更好"的数据；
- **岗位族扩展**：目前 3 个，缺"设计/产品/运营"，需要新变体与新的筛人逻辑；
- **渲染后端**：HTML/LaTeX 模板，让非 Word 用户也能用；
- **成本控制**：把"质检 3 轮"改成"按需 1 轮 + 人工点选"，可省 40% token。
